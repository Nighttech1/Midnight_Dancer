# Codex — Midnight Dancer

## Рабочая база

- Актуальная разработка: `kmp/` (shared Kotlin, Android Compose, iOS SwiftUI).
  Flutter-документацию сверять с текущим кодом.
- До работы читать `.cursor/rules/README.md`, правила и skills нужных ролей,
  актуальную волну в `memory/waves/`. Не читать все внешние библиотеки навыков подряд.
- Существующие незакоммиченные изменения сохранять. Не делать reset/clean и не
  перезаписывать чужую работу. До продуктовых изменений оформить spec/chain.

## Реальные субагенты

Пользователь просит видимую работу команды. Для инженерных задач (ревью,
валидация, реализация, исправления) использовать реальные инструменты субагентов.
Главный агент — Оркестратор. Назначать только нужные роли из существующего реестра.
Для коротких объяснений и простых правок документов запуск команды необязателен.

- Перед запуском сообщить роль, конкретную задачу, разрешённые пути и ожидаемый результат.
- В chain записывать соответствие роли фактическому имени/ID запущенного агента.
  Роль, исполненная главным агентом, явно обозначается как его этап, а не отдельный агент.
- Параллелить независимые задачи. На каждый изменяемый путь — один писатель.
  Независимый ревьюер не должен одновременно править проверяемые файлы.
- Результат исполнителя передавать ревьюеру/Тестировщику; находки возвращать владельцу
  с конкретным запросом. Не приписывать агенту работу, которую он не выполнял.
- Если инструменты субагентов недоступны, сообщить это и явно описать работу
  одного исполнителя. Не изображать переписку вымышленных агентов.
- Не запускать все роли ради демонстрации процесса. Не менять модель/усилие
  субагентов без явного основания в инструкции пользователя или применимом skill.

## Видимый процесс в чате

По запросу пользователя от 2026-11-08 промежуточные сообщения разрешены и обязательны.
В вопросах видимости процесса это заменяет прежнее требование показывать только
финал Клиента со словом «согласовано» в CLAUDE.md, client.mdc, orchestrator.mdc,
skills и документах цикла. Критерии самой приёмки при этом сохраняются.

Публиковать краткие фактические обновления:

1. Назначение: `Оркестратор → Тестировщик [имя]: задача, границы, ожидаемое доказательство`.
2. Находка: `Тестировщик [имя] → Оркестратор: факт; риск; файл/тест/лог`.
3. Передача: `Оркестратор → Фиксер [имя]: находка и требуемое исправление`.
4. Проверка: кто проверил, какой командой/сценарием, результат и ограничения.

Каждое реальное назначение, существенную находку, блокер, решение по риску и
вердикт показывать своевременно. При длительной работе обновлять статус хотя бы
раз в минуту, без повторения неизменившихся сведений. Передавать краткое содержание
реальных сообщений; дословную цитату маркировать и использовать только при наличии
соответствующего сообщения. Не выдумывать споры. Не публиковать внутренние цепочки
рассуждений, секреты или избыточные сырые логи.

Для риска указывать серьёзность, основание, практическое последствие, владельца
и следующий способ проверки. Гипотезы отделять от подтверждённых дефектов.

## Доказательства и завершение

- Отделять старые отчёты от актуальных запусков. Наличие APK не доказывает
  соответствие рабочему дереву. Не объявлять PASS без выполненной проверки.
- Для волны вести `chain.md`, `status.md` и `agent-events.md` в её папке:
  участник, назначение/передача, результат, риск, ссылка на доказательство.
  Журнал содержит события работы, а не внутренние рассуждения.
- Финал: вклад каждого фактически запущенного агента, изменённые файлы,
  выполненные проверки, оставшиеся риски, артефакт и статус приёмки.
- Клиент/независимый ревьюер не принимает собственный продуктовый код.
  Не ставить «согласовано», если обязательные проверки не выполнены; честно
  указать непроверенное и конкретный блокер вместо фиктивной приёмки.
- Package/bundle ID сохранять. Production-публикация требует успешной приёмки
  и явного согласования пользователя. Не считать настройку команды разрешением на релиз.
